# 逐任务观察：改善与退化

这些案例来自正式留出测试集的已保存轨迹，用于解释观察到的行为；没有用于本轮后续调参。动态模拟用户的实际回答会变化，不能把一对轨迹当作严格的单因素因果证明。原始文件位置见[runs.json](runs.json)。

## 任务26：从错误业务对象转向查证订单

用户需要找到寄往指定地区的订单，取得物流信息，并退回部分商品、保留其他商品。

- Base：先查询不存在的订单，随后对一笔尚未送达的订单尝试退货；收到业务错误后又尝试不适用的改商品工具，最终因工具错误过多终止，官方任务得分0。
- SFT：依次获取用户和多笔订单详情，在用户确认待退商品与付款方式后，对正确的已送达订单调用退货工具；官方任务得分1。
- SFT + GRPO：本轮在14次工具调用后耗尽上下文预算，按预设失败规则记0；没有工具执行错误。这也说明工具错误率降低，并不保证业务完成。
- 能支持的结论：本例观察到订单查证、业务状态匹配与参数使用的改善。不能由此宣称全面政策合规。

## 任务51：执行成功后仍未正确结束

用户提供了不确定的订单号，需要退回一台数码相机并原路退款。

- Base：6次工具调用、1次工具错误，完成退货并正常结束，官方任务得分1。
- SFT：17次工具调用、1次工具错误。曾成功将正确订单更新为`return requested`，随后又重复调用退货/查询工具，最终耗尽交互步数，官方任务得分0。
- SFT + GRPO：7次工具调用、0次工具错误，正常结束且官方得分1。本例恢复成功，但不能据此代替全部40个测试任务的总体结果。
- 能支持的结论：工具执行正确不等于整个Agent任务成功；识别已有执行结果、避免重复操作并适时结束，同样影响成功率。训练集loss下降也不会保证每个测试任务都改善。

完整的失败转成功、成功转失败数量与任务编号见[实验报告](report.md)；[逐任务结果表](task_results.csv)保留全部案例，而不只展示这两个例子。
