# 为什么原 GRPO 会退化：证据与待验证假设

本次没有把“GRPO不适合客服”当作结论，而是分开检查实现、学习信号和评测波动。最终任务成功率见 attention_report.md，全部开发对照见 report.md。

## 最终复测及诊断结论

相同40个测试任务、seed42/43各执行一次：SFT为7/40、6/40，修复后的F均为9/40。汇总13/80→18/80，即16.25%→22.50%，观察提升6.25个百分点；平均工具调用10.25→9.5875，重复调用199→158，预算耗尽44→38。逐任务配对12次改善、7次退化。按任务聚类的95% bootstrap差值区间[-5.00,+17.50]个百分点包含0，两个评测种子也不代表多次独立训练。

这里比较的是原SFT与整套修复后的GRPO，不能把6.25个百分点全部归因于掩码、KL或某个奖励项。E与F的开发结果及独立数值实验支持继续研究掩码影响，尚不构成其测试性能贡献的独立量化。

F的三个开发检查为3/15、2/15、0/15，说明修复实现后继续更新仍可能退化。因此最终使用开发规则预先选定的step8（32条轨迹、7次更新），而非整轮96条、21次更新后的最后权重。业务进度奖励让失败组参与更新，但给整条失败轨迹相同优势可能同时强化后续低效动作；这仍是待验证的信用分配假设，不能写成已证实原因。

本轮确认的贡献是：修复真实的训练/采样兼容性问题，补齐可靠恢复与证据链，并在冻结条件下观察到正向任务变化。下一轮应优先在训练/开发任务上验证分段信用分配和更新早停，再使用新的外部任务或多个独立训练种子验证；不得继续利用本轮测试成绩选参数。

## 已确认的实现问题

- 采样端 vLLM 使用 BF16 基座，原训练端使用4-bit基座；同一适配器不保证两端策略概率相同。
- 原概率归一化在低精度计算。固定首批输入重放中，log-prob MAE从0.107921降至0.044421，概率比超出[0.8,1.2]的比例从13.93%降至5.60%。这是BF16训练与FP32归一化的组合修复证据，不是独立归因，也不是任务成功率。
- ART准备了packed input_pos，但共享Unsloth前向没有传入。项目适配层补传position_ids；随机小型Qwen2数值测试验证分支前向与独立前向一致。上述实际重放首批没有位置重置，不能把该批改善归因给此项。
- 更深入复核确认：锁定Unsloth的CausalLM入口无条件覆盖ART的分支注意力掩码。位置编号正确也无法阻止后一个分支看到前一个分支。已安装函数的控制流复现和实际Unsloth/xFormers GPU测试均验证该问题；F在decoder入口保留原掩码，并适配GQA张量维度。实际随机小Qwen2的分支隐藏状态最大偏差4.1875→0.02246，反向梯度有限且非零。这是前向/反向正确性证据，不是任务性能提升。
- 原ART恢复路径没有保存本项目需要的优化器状态。新增Adam/RNG保存恢复，并避免恢复后额外warmup改变已恢复动量；CPU测试验证恢复后的下一步与连续运行一致，不承诺云端用户完全确定。

## 已确认的学习信号缺口

原实验28个采样组只有10组更新。本轮仅结果奖励组24组中16组全失败；对训练轨迹严格离线重放，发现其中9组存在业务进展差异，17条失败轨迹实际执行了至少一个正确目标写操作。二值结果奖励无法区分这些轨迹。

只惩罚重复调用、工具报错和耗尽预算也有局限：调用合法不代表业务选择正确。开发task44中，模型把$150.01的商品误认为比$135.24更便宜，随后执行合法但错误的换货。工具无报错，DB目标和退款断言失败。

新增业务进度组在轨迹结束后匹配目标读/写操作并验证执行成功，结合DB目标达成提供最多0.5的辅助奖励。总过程惩罚最多0.3，故最差完整成功0.7仍高于最佳失败0.5。重复动作只计一次，失败调用不计分；任务目标只进入训练奖励，不进入模型输入。全失败组仅在业务进度存在差异时才允许更新。

该奖励仍是整条轨迹级别的分数，不是逐token或每步价值函数；提高有效更新比例也不自动意味着成功率提高。

## 不能从现有证据推出的结论

- 预算耗尽不等于“业务已经完成，只是不停止”：旧训练50条符合条件的预算失败中，仅7条DB分量已达标。
- 工具错误率不等于全面政策违规率，当前没有完整合规验证器。
- 一次开发成功率持平不表示行为不变：consistent首轮与SFT同为3/15，但为3个任务改善、3个任务退化。
- 动态模拟用户会影响路径：上述最低价案例中，SFT轨迹的用户纠正了模型，新轨迹的用户接受了错误建议。单例差异不能全部归给训练。
- 两个评测种子不是两个训练种子。五个候选均在小开发集上选型，最终需报告完整冻结测试及不确定性，不能把最佳开发检查点当作测试提升。

## 掩码问题如何影响GRPO

采样记录的旧概率以单条轨迹的合法历史为条件；训练时如果共享前缀后的其他分支可见，训练概率就额外依赖另一条轨迹。此时重要性采样比不再只衡量策略参数的变化，即使更新前也可能偏离1，进而影响裁剪和优势加权。训练中的固定参考模型若也使用同样错误上下文，较小KL并不能证明训练与真实采样分布一致。

这解释了为什么“损失有限、KL很小”仍不足以排除实现问题。当前证据证明掩码兼容性错误及修复正确性；它在成功率退化中占多大贡献，需要F与E的任务对照，不能直接断言所有退化均由掩码导致。额外3B只读重放的4个冻结序列均无分支位置重置，不能用其小幅数值变化作为3B分支隔离的因果证据。

## 对照如何回答问题

| 比较 | 要检查的问题 |
|---|---|
| outcome → kl | SFT参考KL是否约束策略退化 |
| kl → shaped | 加入有界过程惩罚及全失败组筛选是否有效 |
| shaped → consistent | 统一基座精度、FP32归一化和位置修复的整体效果 |
| consistent → progress | 业务进度辅助奖励及对应组筛选能否利用原先丢弃的失败轨迹 |
| progress → attention | 保留ART分支掩码能否改善真实任务结果；随机小模型GPU测试单独验证前向/反向正确性 |

每组从相同原SFT权重启动，同一任务课程、24组×4条采样、学习率和开发检查时间。实际更新次数允许不同，这正是奖励能否提供有效学习信号的一部分。上表不是各子改动的独立因果证明。
